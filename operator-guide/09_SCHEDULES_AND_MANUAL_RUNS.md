# 09. Расписания и ручные запуски

## Operator Consistency Rule

В этом разделе:

- `Реальное поведение (verified)` — подтверждено текущими маршрутами и проверками;
- `Целевое состояние оператора (operator goal state)` — желаемый режим работы;
- `Ещё не реализовано (not implemented)` — пока нет подтверждённой функции.

## Запуск по расписанию

`Ещё не реализовано (not implemented)`:

- в подтверждённых операторских маршрутах нет отдельного интерфейса управления расписанием;
- нельзя описывать расписание как готовую кнопку в Telegram или готовый UI.

`Целевое состояние оператора (operator goal state)`:

- оператор задаёт время запуска;
- может отключать расписание;
- видит последний успешный запуск по расписанию.

## Ручной запуск

`Реальное поведение (verified)`:

- ручной запуск доступен через API-маршруты запуска;
- контрактный запуск через `POST /contracts/{contract_id}/run` подтверждён на живом контуре.

## Отключение расписания

`Ещё не реализовано (not implemented)`:

- подтверждённого операторского маршрута для включения/выключения расписания сейчас нет.

## Повторный запуск

`Реальное поведение (verified)`:

- повторный запуск возможен как новый запуск с новым `run_id`.

`Частично подтверждено (partially verified)`:

- в обычном `POST /actions/run` есть риск отказа по коннектору в текущем контуре (`connector_denied`);
- поэтому повторный запуск безопаснее делать только после проверки причины прошлой ошибки.

## Когда оператору безопасно запускать повторно

- причина прошлого сбоя понятна;
- журнал прочитан;
- среда проверена;
- запуск не ждёт решения человека;
- нет признака, что действие уже успешно выполнено.

## Риск двойного запуска

- повторить вручную без проверки старого `run_id`;
- повторить действие после частичного успеха;
- запустить сразу несколько раз “на всякий случай”.

Практическое правило:

- сначала проверить статус прошлого запуска;
- только потом принимать решение о повторе.

## Статус кнопок расписания в Telegram

`Целевое состояние оператора (operator goal state)`:

- отдельные кнопки для управления расписанием.

`Ещё не реализовано (not implemented)`:

- подтверждённого рабочего Telegram-меню с расписаниями в этом pass нет.

## Будущий скилл Codex

### `mova-schedule-manager`

Назначение:

- сопровождать расписания запусков и безопасные ручные повторы.

Вход:

- среда;
- контракт;
- желаемое время/частота;
- последние статусы запусков.

Выход:

- подтверждённый план запусков и безопасных повторов.

Проверки:

- запуск не дублируется без причины;
- ручной запуск не конфликтует с уже идущим;
- оператор видит историю последних запусков;
- тестовый и рабочий контур не смешаны.

Запреты:

- не запускать “вслепую” несколько раз;
- не выдавать несуществующие scheduler-функции за готовые;
- не пропускать проверку предыдущего `run_id`.
